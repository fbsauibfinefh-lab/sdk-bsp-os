# 实验规模判断与仿真验证方案

## 直接结论

三块开发板可以作为论文的真实硬件验证集，但不能单独承担 CCF B 或学校 B 区论文的全部实验分量。比较稳妥的证据结构是：

1. 7 个跨厂商 SDK 验证语义恢复的泛化能力。
2. 3 个真实 SDK、2 个 RTOS、6 组工程验证生成、编译、链接和设备模型接入。
3. 3 块真实开发板验证启动和外设语义。
4. native_sim、QEMU 或 Renode 提供高重复次数、故障注入和回归稳定性实验。

在这一组合中，三块板是足够合理的硬件样本下限。它们覆盖 RISC-V 64 位、Arm Cortex-M3、Arm Cortex-M33，且 RT-Thread 与 Zephyr 的设备模型和构建系统不同。是否达到 B 级最终仍取决于创新表述、对照方法、实验严谨性和目标会议审稿标准，不能由板卡数量保证。

| 层次 | 当前规模 | 能支持的结论 |
| --- | --- | --- |

| 工程生成 | 3 芯片 × 2 RTOS | 两种设备模型和构建系统均可生成 |

| Zephyr 主机仿真 | 20 次启动，140 条命令 | 协议、线程、GPIO 模拟和定时器回归 |
| 真实硬件 | 待执行 | 启动、真实 UART/GPIO/中断/定时器语义 |

## 三块板的上板实验要求

每块板应分别运行 RT-Thread 与 Zephyr，形成 6 个“板卡-RTOS”实验单元。每个单元至少执行：

- 冷启动 30 次，记录启动成功率、均值、标准差、P50、P95 和最大启动时间。
- UART 回环、GPIO 电平、GPIO 中断、定时器单次和周期回调各 100 次。
- 连续运行 2 小时或更长，记录自测次数、超时、错误和复位次数。
- 对生成工程执行 clean build 10 次，记录成功率、总时间、诊断轮数和修复数。
- 固定 SDK、RTOS、工具链、板级连接和测试脚本版本，保存原始逐行 JSON 日志。

GPIO 中断需要输出脚连接输入脚，UART 需要 TX/RX 回环。若板载 LED 或串口连接不同，应在实验配置中显式记录引脚，不允许把 `unsupported` 当作通过。

## 已完成的 native_sim 实验

仓库已加入 Zephyr `native_sim/native/64` 后端配置和进程传输层。它使用与实板完全相同的请求 ID、逐行 JSON 协议和主机汇总代码。当前实际结果为：

- 20/20 次启动成功，启动成功率 1.0。
- 平均启动等待 1.059 ms，范围 0.957 至 1.287 ms。
- 140 条命令中 100 条适用并全部通过，40 条需要真实连线的命令标为 unsupported。
- 构建得到 985,712 B 的 x86-64 ELF，text/data/bss 为 29,707/1,005/5,188 B，验证符号全部进入产物。

复现命令：

```bash
./scripts/run_zephyr_native_simulation.sh
```

Zephyr 官方说明 `native_sim` 是硬件无关的 POSIX 仿真板，可运行 UART、GPIO emulator、counter 等模型，并支持覆盖率与 sanitizer。参考：[Zephyr native_sim](https://docs.zephyrproject.org/latest/boards/native/native_sim/doc/index.html)。因此本结果用于证明协议和 OS API 回归，不用于证明 K210、STM32F103 或 PSoC E84 寄存器行为。

## 建议增加的仿真实验

### QEMU 架构回归

建议增加 Zephyr `qemu_cortex_m3` 和 `qemu_riscv32`，分别代表 Arm Cortex-M 和 RISC-V。Zephyr 官方维护这些目标，并支持通过 `west build -t run` 运行。参考：[Zephyr QEMU targets](https://docs.zephyrproject.org/latest/boards/qemu/index.html)。

RT-Thread 可使用已有 `qemu-vexpress-a9` 和 `qemu-virt64-riscv` BSP。安装 QEMU 后，把启动命令交给 `bspforge-hwtest --command`，复用同一协议。建议每个目标运行 100 次启动和 1,000 次命令回归，并在 CI 中保留失败日志。

QEMU 实验主要增加架构和 RTOS 组合的重复性，但不能替代三块板的真实外设测试。

### Renode 外设与故障注入

对于 Renode 已有机器描述的 Cortex-M/RISC-V 平台，可把生成 ELF 加载到 Renode，通过 UART 注入命令，检查 GPIO、定时器和中断状态。Renode 支持 Robot Framework、UART 输入输出、内存和外设寄存器检查，适合自动化测试与故障注入。参考：[Renode testing](https://renode.readthedocs.io/en/latest/introduction/testing.html)。

建议故障场景包括：延迟中断、丢失 UART 字节、错误时钟频率、GPIO 输入抖动、定时器超时和重复复位。每个场景报告检测率、误报率和诊断定位时间。

如果没有与三块实板精确对应的公开机器模型，应选用架构相同且外设模型完整的平台，并明确称为“后端鲁棒性实验”，不能写成目标板仿真。

## 推荐的论文实验表

主文建议保留五张核心表：

1. 7 个 SDK 的规模、版本、能力适用性和真值数量。
2. BM25、fixed、learned、hybrid 的 SDK 留一排序结果、置信区间和显著性。
3. 证据与模块消融，包括无头文件实体、无目标资产筛选、无诊断反馈和无学习重排序。
4. 3×2 工程生成与固件构建结果，包括时间、闭包规模、诊断轮数和镜像大小。
5. 3×2 实板结果，包括启动率、外设通过率、P95 时延和稳定性。

仿真结果可作为第六张表或附录，强调高重复次数、故障注入和可复现性。只增加大量仿真板而不增加真实语义或对照，不会自然提高论文层次。

## 投稿前必须补齐

- 第二位标注者独立复核真值并报告一致性。
- 三块板六种固件的真实回归原始数据。
- 当前已提供不使用结构化证据的标准 BM25 合理替代基线；若目标会议存在任务接口兼容的公开工具，还应增加该工具的端到端对照。
- 对失败案例分类，解释哪些能力因宏、条件编译、芯片多实现或构建规则而无法自动恢复。
- 明确固定 0.75 仅是敏感性结果，主结论采用嵌套选择结果。
