# H03 真值复跑与 LambdaMART 头部排序优化 v0.5
## 1. 结论摘要

本轮使用源码仲裁真值 `human-adjudicated-h03` 重建全部训练数据、硬件效果图和冻结代码向量，并在厂商独立五折上重新评估 v0.3 多视图 LambdaMART。H03 使严格 P@1 从 H02 的 0.651 提高到 0.697，MAP 和 nDCG@10 分别提高到 0.689 和 0.751；Recall@5 从 0.748 降到 0.738，因为 H03 为部分查询补充了多个有效函数，指标分母随之增大。

对外部建议中的 Top-K 目标、符号去重、硬负样本和厂商特征剔除进行了统一消融。三随机种子中，唯一稳定改善 P@1 的改动是把 LambdaMART 的排序截断层级由默认 30 对齐到 Top-5。该配置平均 P@1 为 0.719、MAP 为 0.697、nDCG@10 为 0.755；P@1 相对同脚本默认目标平均提高 0.034。配对 bootstrap 的 P@1 区间仍跨 0，故当前称为候选优化，不作统计显著性主张。

硬负样本首轮最优值没有跨随机种子复现，符号去重和厂商风格特征剔除也没有稳定超过全候选 Top-5。因此这些方案保留为消融，不进入当前候选主配置。默认 Resolver 的确定性 q4 运行路径没有修改。

## 2. H03 数据边界

H03 是 H01 与 H02 候选并集的源码仲裁结果，不是第三位独立工程师标注。其校验结果如下：

| 项目 | 数值 |
| --- | ---: |
| manifest 中训练 SDK | 22 |
| 操作查询组 | 418 |
| `complete` 组 | 284 |
| `no_public_api` 组 | 134 |
| 最终分级候选 | 1,009 |
| 等级 0/1/2/3 | 162/259/178/410 |
| 外部板卡 SDK 泄漏 | 0 |
| 宏候选泄漏 | 0 |

数据集构建时仅 284 个具有可达函数正例的组进入函数排序。它们来自 20 套实际有完整查询的 SDK、18 个独立上游/厂商组。三块板卡的 50 个操作组保持 `external-test`，不参与训练、外折选择或本轮方法选择。

## 3. 数据重建流程

输入依次经过以下步骤：

1. `build_operation_dataset.py` 读取 H03，按操作契约恢复候选并对齐 0/1/2/3 级标签；输出 `dataset-h03-base.json`。
2. `add_cached_field_late_interaction_scores.py` 复用 H02 的 MiniLM 字段分数，对 H03 新候选补编码；复用 22,967 对，新增 7,292 对。
3. `add_structured_retrieval_scores.py` 计算源码角色、签名/操作契约、调用邻居、API 家族和多通道 RRF；输出结构化数据集。
4. `add_hardware_effect_graph_features.py` 从源码、头文件和 IR 调用边恢复寄存器锚点、跨过程效果和公共 API 角色；输出 H03 硬件效果数据集。
5. 两个冻结 Jina 缓存脚本使用新增增量模式，只编码文本哈希不一致的实体。完整视图复用 21,742、编码 1,230 个；操作条件效果视图复用 28,223、编码 2,036 个。
6. v0.2 和 v0.3 均在 H03 上重新运行，避免把 H03 方法与 H02 对照记录直接配对。

增量缓存只在 `(实体键, 序列化文本 SHA-256)` 同时相等时复用向量，因此标签变化本身不会污染代码表示，源码/序列化变化也不会误命中旧向量。

## 5. 训练优化定义

### 5.1 Top-K 截断目标

LambdaMART 仍学习 H03 的 0/1/2/3 分级相关性。通过 `lambdarank_truncation_level=5`，Lambda 计算重点放在排序头部，而不是默认的更长列表。树规模固定为 7 叶、最大深度 4、学习率 0.025，并保留 L1/L2 与特征子采样。该改动不改变候选、特征或推理时硬约束，仅改变训练错序对的头部权重。

### 5.2 符号级去重

同一查询中可能存在同名声明、静态内联和定义。训练去重版本按符号保留最高标签，再以语义难度和稳定实体 ID 选择代表。评测一直按唯一符号计算，因此该消融用于检查训练/评测粒度是否需要完全一致。结果没有稳定超过保留全部实体的版本。

### 5.3 语义硬负样本

未标注候选的难度分数定义为：

```text
0.30 * static_score
+ 0.30 * cosine(query, full_code)
+ 0.30 * cosine(query, focused_effect)
+ 0.10 * multi_channel_rrf
```

每个查询保留全部分级正例，并比较 20、40、80 个最高难度未标注符号。该过程不读取外折标签以外的信息，且只作用于训练组。20 个候选不足以覆盖多种高相似混淆；80 个在首轮较好，但随机种子间 P@1 为 0.722/0.701/0.697，没有形成稳定优势。

### 5.4 厂商风格消融

消融删除 `driver-path`、`field-file-maxsim`、`hal-abstraction`、`private-api`、`source-role-prior` 和 `test-example`。这些字段不含厂商 ID，但可能间接反映 SDK 目录与抽象风格。删除后平均 P@1 为 0.687，低于全候选 Top-5 的 0.719，说明源码层级信息在当前任务中也承担通用 API 边界识别，不能简单按“可识别厂商”全部剔除。

## 6. 评测协议

- 外层：按 18 个 `independence_group` 做五折 OOF，测试折厂商不进入训练。
- 内层：只在外层训练 SDK 内选择配置；外层标签不参与选择。
- 随机种子：20260905、20260917、20260929。
- 分母：284 个 H03 `complete` 查询，任何低分查询都不删除。
- 外部板卡：K210、STM32F103、PSoC E84 共 50 组，仅作历史诊断。
- 正式指标：严格 P@1、Recall@5、MAP、nDCG@10。
- 任务辅助指标：Hit@5，表示前五名是否至少出现一个 H03 正函数。

## 7. 实验结果

### 7.1 真值校准前后

| 真值与方法 | P@1 | Recall@5 | MAP | nDCG@10 |
| --- | ---: | ---: | ---: | ---: |
| H02 v0.3 严格嵌套 | 0.651 | 0.748 | 0.681 | 0.743 |
| H03 v0.3 严格嵌套 | **0.697** | 0.738 | **0.689** | **0.751** |
| H03-H02 | +0.046 | -0.009 | +0.008 | +0.008 |

H03 明显修正了部分 Top1 假错误。Recall@5 小幅下降不表示首个可用函数更难找到，而是 H03 给每组标出了更多有效函数，Recall@5 要求前五名覆盖这些函数。H03 平均每组有 2.366 个唯一正符号。

### 7.2 三随机种子平均值

| 方法 | P@1 | Recall@5 | MAP | nDCG@10 | Hit@5 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 默认全候选 | 0.685 | **0.740** | 0.686 | 0.747 | **0.903** |
| 全候选 Top-5 | **0.719** | 0.737 | **0.697** | **0.755** | 0.899 |
| 符号去重 Top-5 | 0.698 | 0.743 | 0.691 | 0.752 | 0.899 |
| 20 硬负样本 Top-5 | 0.651 | 0.728 | 0.660 | 0.724 | 0.891 |
| 40 硬负样本 Top-5 | 0.694 | 0.740 | 0.690 | 0.752 | 0.901 |
| 80 硬负样本 Top-5 | 0.707 | **0.746** | 0.696 | **0.755** | 0.898 |
| 40 硬负样本 Top-10 | 0.685 | 0.740 | 0.687 | 0.747 | 0.898 |
| 厂商风格剔除 | 0.687 | 0.744 | 0.693 | **0.755** | **0.903** |

全候选 Top-5 的 P@1 三次为 0.722/0.725/0.711，均值 0.719、总体标准差 0.006。相对 H03 原严格嵌套的 P@1 差值为 0.025/0.028/0.014，但三次查询级 bootstrap 95% 区间均跨 0。它是方向稳定、效应量较小的候选优化，而不是已经证明显著的最终升级。

## 8. Top1 与调用等价解释

严格 P@1 只要 Top1 符号不在 H03 正集合中就记 0。SDK 中确实存在以下低估来源：

- 公共包装函数直接调用真值函数；
- 真值公共 API 调用更底层、签名仍可封装的辅助函数；
- 参数化通用 API 与专用包装 API 均能实现同一能力；
- 一个操作需要多个 API 的顺序组合。

本轮对全候选 Top-5 首次运行的 79 个严格错误做直接调用诊断：9 个 Top1 是通过角色、硬约束和复合度检查的公共包装函数，并直接调用 H03 正函数；另有 10 个是 H03 正函数调用预测辅助函数。只把前一类视为“待人工确认的保守上界”，P@1 可从 0.722 到 0.754；若把任意方向直接调用都算入，上界为 0.789，但该口径会错误接纳内部 helper，不能用于正式结果。

因此，P@1 较低具有部分可解释性，但不能用 Recall@5 或调用关系替代。当前自动绑定实际写入 Top1，不会自动尝试五个候选；只有 Top1 行为正确才能直接支撑无人值守固件生成。Recall@5 更适合衡量候选召回与后续编译/人工重排空间。

Hit@5 为 0.901，说明 90.1% 的查询能在前五名找到至少一个 H03 正函数；正式 Recall@5 为 0.740，表示前五名覆盖全部已标有效函数的平均比例。两者同时报告才能回答“是否找到一个可用实现”和“是否完整找回等价实现集合”两个不同问题。

## 9. 与固件可靠性的关系

语义排序指标是固件可靠性的必要证据，不是充分条件。编译和链接只能证明签名、依赖与资产闭包成立，不能证明寄存器效果、初始化顺序、中断上下文和时序正确。当前严格 P@1 约 0.72，即使保守调用上界约 0.75，也不足以单独声称 19 个操作全部自动绑定后固件普遍功能完备。

论文应把可靠性证据分成四层：

1. 厂商独立函数排序：严格 P@1、Recall@5、MAP、nDCG@10 和 Hit@5；
2. 类型/构建闭环：生成工程的编译、链接、镜像与诊断迭代；
3. 操作级行为测试：每个绑定的寄存器效果、模拟器或主机协议回归；
4. 三块实板：启动、UART、GPIO、定时器和中断的可重复上板记录。

上板前可用 H03 Top-5 加编译/类型约束做第二阶段选择，但必须单独评测“最终被写入绑定的 Top1”，不能用 Top-5 命中率冒充自动绑定准确率。

## 10. 当前保留与后续工作

当前保留：

- H03 作为 H01/H02 仲裁后的主要函数排序真值；
- `lambdarank_truncation_level=5` 作为 v0.3 的候选训练优化；
- `Hit@5` 与严格 Recall@5 并列报告；
- 直接调用关系只作为漏标审计和人工复核队列；
- 增量冻结向量缓存作为工程能力。

当前不保留为主配置：固定 20/40/80 硬负样本、符号级训练去重、厂商风格特征剔除、跨厂商混合 qid、目标板卡微调。

下一步优先级是：对 9 个安全包装候选做 H03.1 人工复核；用编译/签名可行性对 Top-5 做无标签重排；在从未参与开发的新 SDK 上冻结执行一次确认评测；最后用三块实板记录最终绑定的操作级行为。若新确认集不支持 Top-5 截断增益，则论文仍使用 H03 v0.3 作为主结果，并把本轮作为训练目标消融。
