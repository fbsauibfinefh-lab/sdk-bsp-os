# 基于 LambdaMART 的 SDK 能力操作定位方法与三板外部评估（v0.6）

## 1. 当前结论

论文和项目计划以 LambdaMART 为最终语义决策模型。它不是只看函数名，也不是让模型直接阅读整个 SDK 后猜一个答案，而是先把 SDK 转换成结构化 IR，为每个候选函数提取名称、签名、源码、调用图、寄存器效果和源码层级等证据，再由轻量级 LambdaMART 学习这些证据应如何组合，输出每项能力操作的函数排序。

本轮使用更新后的三块板卡真值进行了严格复测。结果不支持“现有 LambdaMART 已稳定优于层级约束字段迟交互与 API 家族覆盖解码”这一结论。冻结的三种子 LambdaMART 在原始 H03 外部集上的汇总 P@1 为 0.618，而 q4 结构方法为 0.836。新增结构先验、等价仲裁和两轮通用可行性保护后，三板 P@1 提高到 0.891，三板均超过 0.80，nDCG@10 为 0.808；但 Recall@5 为 0.775、MAP 为 0.736，训练厂商外折也没有证明残差分支优于纯 LambdaMART。因此，本方法仍是论文的目标主方法，但当前版本尚未具备冻结并接入最终六套固件的证据条件。

本轮没有执行新的 K210 上板测试。现有 K210 固件由 `operation-weighted` 解析器生成，不是本轮 LambdaMART 的输出；在 LambdaMART 尚未接入 Resolver 前使用该固件，只能验证后端和测试基础设施，不能验证论文拟采用的完整方法。

## 2. 通俗的完整流程

可以把系统理解为以下七步。

1. 读取 SDK。系统解析源文件、头文件、构建规则、链接脚本和启动文件，把散落在目录中的信息整理成统一的 SDK Migration IR。
2. 明确要找什么。系统把时钟、中断、UART、GPIO 和定时器展开为 19 个能力操作，例如 `uart.write`、`gpio.configure` 和 `timer.stop`，每个操作都有与厂商无关的行为说明。
3. 生成候选。系统先用能力名称、动作词、函数签名、文件路径和调用关系进行高召回检索，从大量函数中保留可能相关的候选，不在这一步直接决定答案。
4. 为每个候选收集证据。证据包括函数名和签名是否匹配、函数处于 HAL/驱动/示例中的哪一层、函数体做了什么、调用链最终是否触达寄存器、是否出现相反动作，以及是否属于错误架构或无关外设。
5. 用 LambdaMART 排序。每个“SDK + 能力操作”构成一个独立查询组。模型比较同组候选，学习哪些证据组合通常对应 3 级直接 API、2 级可替代 API、1 级相关步骤和 0 级未标注候选。
6. 执行可行性保护。与目标 CPU 架构冲突、来自示例回调、属于无关外设私有中断入口或不满足操作契约的候选不能进入最终绑定首位。
7. 输出绑定并进入工程闭环。冻结模型的 Top1 写入绑定计划，TopK 和全部证据留作审计；随后 Closure Solver 补齐构建资产，OS Backend 生成 RT-Thread 或 Zephyr 工程，Build Diagnoser 依据编译错误迭代修复，最后生成固件并执行上板验证。

## 3. 输入及预处理

### 3.1 SDK Migration IR

模型不直接消费原始目录，而是消费 SDK Ingestor 生成的 IR。函数实体至少包含：

| 字段 | 作用 |
| --- | --- |
| `entity_id` | 由来源和位置稳定生成的实体标识，用于跨阶段追踪 |
| `symbol` | 函数或类方法名称；类方法按所属类型和签名规范化为可调用实体 |
| `signature` | 返回类型、参数类型、参数名及可见修饰信息 |
| `file`、`line` | 定义或声明位置，用于源码层级判断和证据回溯 |
| `calls` | 直接调用的函数，用于构造跨过程调用图 |
| `includes` | 直接头文件依赖，用于接口可见性和闭包求解 |
| function body | 归一化函数体，用于代码编码和寄存器副作用提取 |
| build evidence | 文件所属组件、条件宏、目标架构和构建规则 |

混合前端依次尝试 Clang AST、tree-sitter 和正则兜底。AST 适合恢复类型和方法，tree-sitter 在缺少完整编译参数时保持较好的结构恢复率，正则只负责前两者无法处理的残余文件。每个实体记录实际解析前端和置信度，避免把兜底结果与完整 AST 等价处理。

### 3.2 操作查询

查询由 `capability.operation` 和操作契约组成。当前五类能力共 19 个操作：时钟 4 个、中断 4 个、UART 3 个、GPIO 4 个、定时器 4 个。契约描述该操作应产生的行为、常见同义词、参数角色、可接受的低层实现和冲突动作。例如 `uart.write` 要求向 UART 发送一个字节或缓冲区，`receive/read` 是冲突动作；`interrupt.register` 要求安装处理函数或设置向量，仅设置 pending 位不满足契约。

操作集合固定不等于每个 SDK 都必须存在单一公共函数。宏、回调覆盖或必须组合多个步骤的操作标为 `no_public_api`，不强行制造正函数，也不进入函数级 P@1 分母。

### 3.3 候选生成

候选生成采用高召回原则。系统综合能力词、动作词、签名提示、文件路径、include 和一跳调用关系建立多个召回通道，并保留各通道名次。候选池不是 SDK 全部函数，也不是最后 Top5；它是进入精排前的相关函数集合。已审计真值只用于检查召回上限和离线训练标签，不参与无标签召回分数计算。

## 4. 候选特征

### 4.1 静态与操作契约特征

静态特征把符号拆分为 CamelCase、下划线和数字子词，计算能力词、动作词和签名角色匹配。系统同时记录相反动作、参数化开关、状态查询、私有实现、示例/测试路径、反向 OS 适配器、源码角色和 API 家族。规则只产生可解释特征或不可违反的约束，不再直接用经验权重代替最终学习决策。

### 4.2 字段感知迟交互

`symbol`、`signature`、`calls`、`file` 和 `includes` 分别编码。查询也按字段生成不同文本，例如符号查询强调设备名和动作，签名查询强调 buffer、length、callback 等参数角色。冻结的 MiniLM 为每个 token 产生向量；对每个查询 token，取它与候选字段所有 token 的最大余弦相似度，再对查询 token 求平均。这样可以分别对齐 `uart`、`write` 和 `buffer`，又能缓存候选向量。

该通道是语义证据之一，不是最终决策器。此前 q4 方法直接使用它和规则解码；当前 LambdaMART 把字段分数及其分项作为输入特征，由树模型决定它在不同操作中的作用。

### 4.3 完整代码和操作条件代码视图

冻结的 `jina-embeddings-v2-base-code` 对两类文本编码。完整视图包含归一化函数体、签名和直接调用；聚焦视图只保留与当前操作相关的条件语句、寄存器读写、赋值、位运算和效果路径邻域。模型使用“查询-完整代码”“查询-聚焦代码”和“完整-聚焦”三个余弦相似度。编码器不在本项目真值上微调，训练部分只更新后续 LambdaMART。

### 4.4 寄存器效果图

系统从寄存器结构、`volatile`/MMIO 访问、位掩码和寄存器宏建立硬件锚点，再沿 caller/callee 图传播到公共 API。每个候选得到直接效果、传递效果、锚点深度、读写方向、能力效果、动作效果、效果纯度、影响广度、公共边界深度、回调倾向和复合函数倾向等特征。

该图回答“函数实际做了什么”，补足函数名和注释可能误导的问题。传播有最大深度和衰减，示例程序、OS 适配器及同时覆盖多类硬件效果的复合入口会得到风险特征，不把反向调用图最上层简单等同于目标 API。

### 4.5 结构先验与目标可行性

本轮把冻结 q4 的候选分数、百分位、倒数名次、与首位间隔以及 Top1/Top3/Top5 标记加入 LambdaMART 特征。这些值是弱结构先验，不读取当前查询标签。

目标可行性保护使用项目本来就已知的目标架构和操作契约。当前实现排除 Cortex-M 目标中的 CMSIS Core_A/Core_R 或 GIC 实现，排除文档、中间件和反向 OS 适配器，排除具有回调证据的示例函数；对通用中断控制操作，还排除 USB、显示、网卡等设备私有中断入口，并要求 `interrupt.register` 出现 vector/register/callback/handler 等绑定动作。所有排除规则针对类别，不包含 K210、STM32 或 PSoC 的函数名白名单。

## 5. LambdaMART 内部工作

### 5.1 为什么使用 LambdaMART

任务需要比较同一操作下的候选顺序，不需要预测一个跨 SDK 统一的绝对分数。LambdaMART 是基于梯度提升树的学习排序方法，能处理连续值、布尔值、缺失值和非线性交互，模型体积小、CPU 推理快，并能输出特征重要性，适合本项目的结构化 IR 特征。

### 5.2 训练样本组织

一个查询组是一个 `SDK + operation_id`。组内候选使用 0/1/2/3 级相关性，模型只比较同组候选，不比较两个 SDK 的原始分数。0 级在训练中表示“当前真值未标为可用”，它用于形成相对偏好，但不被解释为逻辑上已证明错误；因此训练目标是让已确认正函数排在未标注候选前，而不是学习全局二分类边界。

H03 训练数据包含 20 套训练 SDK、18 个独立厂商组、284 个可达查询和约 3.09 万候选。K210、STM32F103 和 PSoC E84 共 55 个可达查询，固定为 `external-test`，不参与模型拟合、树参数选择、残差权重选择或早停。

### 5.3 树模型如何学习

初始时所有候选分数接近。LambdaRank 根据当前排序中每一对不同等级候选交换后造成的 nDCG 变化，计算带位置权重的成对梯度；排在前部且会显著影响 nDCG 的错误获得更大修正。LightGBM 每轮用一棵小树拟合这些梯度，树节点可以学习诸如“有寄存器写效果且位于公共驱动层”“符号像 enable 但来自 USB 私有目录”等非线性组合。最终分数是所有树输出之和。

当前保留配置为 240 棵树、学习率 0.025、7 个叶子、最大深度 4、最小叶节点样本 28，并使用 L1/L2 和列采样。`lambdarank_truncation_level=5` 让训练更关注最终 Top5。该配置来自训练 SDK 内部比较，不由三块板标签选择。

### 5.4 分组隔离与选参

外层五折以厂商/独立来源为单位，整个厂商的 SDK 同时进入训练或测试，避免同厂商命名风格泄漏。每个外层训练折再划出独立厂商做内层验证，选择树配置或融合强度。最终模型使用全部训练 SDK 重训。三块板先用于冻结模型的一次外部评测；本轮根据该结果继续开发后，后续三板结果明确降级为开发诊断，不再冒充完全未见确认结果。

### 5.5 预测和输出

推理时为一个操作的全部候选生成相同顺序的特征向量，LambdaMART 输出实数分数，可行性保护再移除不满足硬条件的候选。系统不因分数低而删除操作，仍按分数输出 Top1 和 TopK，但在证据中记录低分、分差小、通道冲突和约束原因。Top1 才进入 `canonical-binding-plan.json`，TopK 用于人工复核和错误分析。

## 6. 以前已完成的 LambdaMART 优化

1. 从函数名和路径特征扩展到字段语义、完整代码、操作条件代码、调用图和寄存器效果图的多视图输入。
2. 使用 0/1/2/3 分级相关性而不是单一二值标签，并将同一查询内的正函数与未标注候选建模为相对偏好。
3. 将 19 个操作编码为操作条件特征，使同一函数在 enable/disable、read/write、start/stop 下可以获得不同排序。
4. 比较 5/7/9/13 叶、不同深度、L1/L2、列采样和样本采样，使用厂商分组的嵌套交叉验证选择小树配置。
5. 比较默认 LambdaRank、Top5/Top10 截断、符号折叠、20/40/80 个硬未标注候选和厂商风格特征剥离。Top5 截断在多随机种子下最稳定，硬负样本方案未稳定获益，作为消融保留。
6. 使用三个预先训练的随机种子检查方差，并实现查询内 z-score 集成；三板标签不参与种子选择。
7. 建立完整错误报告、调用等价诊断和特征重要性，区分真值漏标、同族动作混淆、无关子系统、错误架构和模型一般排序错误。

## 7. 本轮新增工作

1. 使用更新的三板 H03 真值重建 55 个外部查询，冻结评测三个既有 LambdaMART 种子，并与同候选、同真值下的 q4 比较。
2. 新增结构先验增强 LambdaMART，将 q4 排序压缩为 7 项候选特征；残差形式为 `z(structured_prior) + alpha * z(LambdaMART)`，`alpha` 只在训练 SDK 的内层验证中从 0.10 至 1.00 选择。
3. 新增可复用的标签重对齐工具。工具校验查询、实体和真值符号，只复用与标签无关的既有语义/图特征，并记录输入 SHA-256 和变化数量。
4. 对预测与 H03 不一致的函数逐项回看声明、定义和寄存器效果。确认 3 个等价 API 漏标，以独立的 `external-board-h03-equivalence-r1` 仲裁补丁记录，不覆盖原始结果；其余错误不修改。
5. 新增目标可行性保护和目标架构 profile，处理错误 CPU 架构、示例回调、无关设备私有中断入口和注册契约不满足问题，并增加 4 项专用测试。
6. 完整测试从此前 55 项增加到 61 项，当前 `61 passed`。

## 8. 指标结果

### 8.1 原始更新 H03，未做事后仲裁

| 方法 | P@1 | Recall@5 | MAP | nDCG@10 | Hit@5 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 冻结 LambdaMART 三种子集成 | 0.618 | 0.653 | 0.588 | 0.662 | 0.873 |
| 层级约束字段迟交互与 q4 家族解码 | 0.836 | 0.681 | 0.724 | 0.799 | 0.891 |

这组结果直接否定了“既有 LambdaMART 已优于 q4”的前提，不能从旧训练集指标推导三板泛化结论。

### 8.2 等价仲裁后的结构先验 LambdaMART

源码复核新增三项：K210 `timer_disable`、STM32 `LL_RCC_PLL_Enable` 和 `LL_TIM_DisableCounter`。它们均能独立完成操作，且声明、定义、源码修订和硬件副作用已归档。示例回调、私有 RCC helper、Core_A GIC、USB/图形中断等预测没有改为正例。

| 版本 | P@1 | Recall@5 | MAP | nDCG@10 | Hit@5 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 结构先验 LambdaMART v1.1 | 0.855 | 0.775 | 0.725 | 0.800 | 0.964 |
| 第一轮可行性保护 v2 | 0.873 | 0.725 | 0.718 | 0.785 | 0.927 |
| 补全正向操作契约 v2.1 | **0.891** | **0.775** | **0.736** | **0.808** | **0.964** |

可行性保护改善首位精度，但减少 Top5 中的部分低等级相关函数，因而 Recall@5 下降。这说明 P@1 与“覆盖全部等价 API”的 Recall@5 存在真实权衡，不能只报告其中一个。

### 8.3 v2.1 分板结果

| SDK | 查询数 | P@1 | Recall@5 | MAP | nDCG@10 | Hit@5 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| K210 | 19 | 0.947 | 0.793 | 0.782 | 0.850 | 0.947 |
| PSoC E84 | 18 | 0.889 | 0.769 | 0.729 | 0.798 | 0.944 |
| STM32F103 | 18 | 0.833 | 0.763 | 0.696 | 0.774 | 1.000 |

三板 P@1 均达到 0.80，但 MAP 仍在 0.696 至 0.782 之间，说明首位候选改善后，后续等价 API 的相对顺序仍不稳定。K210 的 Hit@5 也因可行性过滤降为 0.947，不能用汇总平均值掩盖单 SDK 风险。

### 8.4 训练 SDK 的厂商独立交叉验证

| 分支 | P@1 | Recall@5 | MAP | nDCG@10 | Hit@5 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 纯结构先验 | 0.335 | 0.455 | 0.403 | 0.460 | 0.609 |
| 加结构特征的纯 LambdaMART | **0.683** | **0.737** | **0.688** | **0.750** | **0.884** |
| 训练内层选择的先验残差 | 0.500 | 0.623 | 0.561 | 0.621 | 0.785 |

残差分支在三板上 P@1 较高，但在训练 SDK 的严格外折上明显低于纯 LambdaMART，不能作为已经证明泛化的最终组合。它应作为本轮探索结果和失败消融保留。

## 9. 为什么暂不上板

K210 分板语义结果已经较好，但论文主张是一个可泛化的 SDK 操作定位方法，而不是针对 K210 的专用映射。当前有三个不能跳过的缺口：

1. 三板已经用于本轮错误诊断和方法调整，不能再作为调整后模型的完全未见确认集。
2. LambdaMART 尚未接入运行时 Resolver；现有 K210 固件明确由 `operation-weighted` 生成。
3. 三板整体 Recall@5 和 MAP 仍低于预设工程门槛，且新增约束在训练厂商外折上略有退化。

因此本轮不烧录、不运行 IO7-TX/IO6-RX 和 IO8/IO9 测试。连线方案仍然有效，等冻结模型生成新的 K210 绑定、工程和固件后再执行，才能形成“语义定位、代码绑定、编译、烧录、硬件行为”同一条证据链。

## 10. 下一步开发计划

1. 重构训练真值的层级一致性。训练 SDK 和三板真值对 HAL、LL、`static inline`、包装函数和分步 API 的等级口径必须统一；先统计每个来源层的正例比例，再做盲法复核。
2. 扩大高质量训练覆盖。不是简单增加候选行，而是增加带源码证据的独立 SDK 查询，优先补充 STM32Cube/LL、CMSIS、多组件 SDK 和中断控制器；建议至少增加 8 至 12 个独立厂商组。
3. 把目标架构、芯片系列和 SDK 组件图变成一等输入。候选先经过架构/组件可达性筛选，再进入 LambdaMART，避免让排序模型学习本应确定的不可行关系。
4. 采用两阶段模型。第一阶段学习“是否为目标芯片可调用的公共驱动实体”，第二阶段 LambdaMART 只对可行候选排序；两阶段都按厂商分组交叉验证。
5. 对多正例查询采用层级感知目标。区分“可直接绑定的 grade 3/2”与“只能作为相关步骤的 grade 1”，P@1 只把 2/3 级计为可自动绑定，Recall@5 同时报告可绑定召回与全相关召回。
6. 新增一次性确认 SDK。由于三板已经参与诊断，方法冻结后应增加未用于错误分析的新 SDK 做最终语义确认；实体上板仍可使用现有三块板。
7. 达到门槛后实现 `operation-lambdamart` Resolver，导出模型版本、特征 schema、向量缓存哈希和目标 profile，重新生成六套工程，再执行 K210 两种 RTOS 的物理回环和 GPIO 测试。

建议冻结门槛为：每个板卡 SDK 的 P@1 不低于 0.80，三板汇总 MAP 和 nDCG@10 不低于 0.80，Hit@5 不低于 0.90；Recall@5 同时报告但不与 Hit@5 混用。只有达到该门槛且训练外折没有明显退化，才进入最终上板阶段。
