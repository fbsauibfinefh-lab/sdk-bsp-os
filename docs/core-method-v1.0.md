## 1. 一句话主张

本文提出一种面向芯片 SDK Migration IR 的**多视图结构增强 LambdaMART 能力操作定位方法**：联合函数与签名字段语义、操作条件代码表示、寄存器效果图、源码层级和操作契约，在厂商隔离训练下学习候选函数的相对顺序，并将可审计的 Top1 绑定送入 RTOS 后端、构建闭包和自动诊断闭环以生成固件。

论文应始终围绕这句话展开，不要把所有工程模块写成相互独立的创新点。

## 2. 要解决的问题

输入 SDK 中同时存在公共 HAL、低层 PDL/LL、私有实现、RTOS 反向适配、示例、测试和第三方中间件。名称相似不代表满足同一迁移操作，例如：

- 基础硬件定时器与 PWM、Encoder、HallSensor、软件定时器名称相近；
- 系统中断控制器 API 与 SDIO、UART 等外设中断 API 都包含 `irq/register`；
- `set_enabled(bool)` 可同时承担 enable/disable 或 start/stop；
- 同一操作可能存在阻塞、中断、DMA、公共内联或不同驱动层实现；
- 正确 API 可能不在普通语义模型的 Top5 中，但位于高置信 API 的同一功能家族。

因此本文不是普通的“文本到函数语义搜索”，而是带有 SDK 层级、设备契约和组合覆盖约束的代码检索问题。

## 3. 输入与输出

### 3.1 输入

SDK Ingestor 将源码、头文件和构建资产转换为 Migration IR。排序阶段使用以下函数字段：

| 字段 | 内容 |
| --- | --- |
| `symbol` | 函数符号及其标识符子词 |
| `signature` | 返回类型、参数类型与参数名 |
| `calls` | 函数直接调用的 SDK 符号 |
| `file` | 源码相对路径 |
| `includes` | 直接包含的头文件 |
| 图关系 | caller、callee、declaration、definition 和 include 关系 |
| 构建证据 | 文件所属组件、构建规则和目标约束 |

查询由规范化的 `(capability, operation, contract)` 构成。当前覆盖 clock、interrupt、UART、GPIO 和 timer，共 19 个操作。

问题：contract是什么，怎么来的，有什么用。

回答：这里的 `contract` 不是 SDK 中原本存在的某个对象，也不是从真值标签中训练得到的向量，而是**查询侧的操作契约**，用于把“要找什么函数”描述得比 `uart.write` 这类短标签更完整。一个查询由能力 `capability`、动作 `operation` 和契约 `contract` 三部分组成。例如 `uart.write` 的能力是 UART，动作是 write，契约还要表达“向 UART 外设发送缓冲区中的字节，通常涉及 buffer/length，并且不应是 read/receive 或初始化函数”。

契约来自项目中与厂商无关的能力模式和人工定义的设备操作语义，具体落在四类配置中：`CAPABILITY_SCHEMA` 给出能力包含哪些操作及动作别名；`OPERATION_DESCRIPTIONS` 给出每个 `capability.operation` 的自然语言描述；`SIGNATURE_HINTS` 给出期望出现在参数或返回值中的提示词；`CONTRACT_TERMS` 给出优选词和冲突词。参数化开关、相反动作和设备子模式等规则则由 `operation_feature_map()` 补充。它们描述的是 UART、GPIO、timer 等设备模型的一般语义，而不是针对某个 SDK 记忆具体函数名。

契约有三项作用。第一，它参与五个 IR 字段的专用查询构造，使短小的符号字段侧重设备名和动作词，而签名字段同时关注参数角色。第二，它形成操作契约分数，用于降低 PWM、Encoder、局部总线 IRQ、相反读写方向等“名称相似但行为不兼容”的候选。第三，它提供可审计证据：系统可以说明某候选因哪些优选词、冲突词、签名提示或参数化开关获得或失去分数。契约属于查询规范；`symbol`、`signature`、`calls` 等属于候选侧 IR 事实，二者在评分时相遇，不应混写为 IR 的同一字段。

### 3.2 输出

每个操作输出排序候选、最终绑定和可审计证据：

问题：这里的排序候选、最终绑定和可审计证据都是什么。他们三者的关系，各自的具体内容是什么。下面这个文本具体是什么意思。

回答：“排序候选”是针对一个操作返回的 TopK 函数列表。每项至少包含稳定的 `entity_id`、符号名、综合分数、源文件位置、源码角色、API 家族，以及字段、静态、契约和层级等分项特征。它回答“哪些 SDK 函数最可能实现该操作，以及它们的先后顺序”。

“最终绑定”是从排序结果中作出的自动选择。当前 `operation-structured` 方法对每个存在候选的能力操作直接选择最终分数最高的首位函数，并把该函数的 `entity_id` 和签名写入 `canonical-binding-plan.json`。低分、分差较小或通道证据较弱时仍保留该绑定，同时增加复核标记；只有候选池本身为空时才记为 `missing`。最终绑定因此不是另一套检索结果，而是排序首位向后端输入契约的确定性转换。

“可审计证据”是支撑排序和绑定的追溯信息，包括定义文件与行号、解析前端及其置信度、符号和签名匹配、五字段 MaxSim、源码角色及路径依据、操作契约的正负证据、家族归属和候选间隔等。证据随候选保存，最终绑定引用其中的首位实体；低分操作仍保留 TopK、最终选择和原因，便于人工复核。

文本链条表示：系统先接收 `capability + operation` 查询；按最终分数输出选中的 SDK `entity_id/symbol`；同时记录该实体属于哪种源码角色和 API 家族；再列出字段、契约、图和层级证据；最后给出置信度与低分/弱证据状态。它描述的是一次操作映射的输出结构，不是五个互相独立的处理阶段。

```text
capability + operation
  -> selected SDK entity_id / symbol
  -> source role and API family
  -> field, contract, graph and layer evidence
  -> confidence and low-score diagnostic state
```

绑定计划随后进入 OS Backend，生成 RT-Thread 或 Zephyr 原生设备工程。

## 4. 核心方法

核心方法只保留以下三个组成部分。

### 4.1 多通道字段迟交互召回

冻结的 all-MiniLM-L6-v2 分别编码 `symbol`、`signature`、`calls`、`file` 和 `includes`。每个字段使用专用操作查询，通过 token MaxSim 计算迟交互分数：

问题：上面这句话什么意思。冻结的意思是什么？all-MiniLM-L6-v2是什么。怎么编码的。使用专用操作查询是什么意思。token MaxSim指的就是下面这个公式吧，这个公式里面的q_f_i, d_f_j怎么来的，公式的具体操作是什么，结果意味着什么。

回答：`all-MiniLM-L6-v2` 是一个公开的轻量 Sentence-Transformer 编码器，约 22.7M 参数。这里使用它的 Transformer 部分取得每个 token 的隐藏向量，而不是只取整句向量。“冻结”表示运行项目时只做前向推理，模型参数不反向传播、不用本项目真值微调；因此相同模型版本、文本和参数会得到确定的字段向量。它不是生成式大语言模型，也不生成代码。

编码时，候选函数先从 Migration IR 组织成 `symbol`、`signature`、`calls`、`file`、`includes` 五段文本。查询也不是对五个字段重复使用同一句话，而是由 `operation_late_queries()` 为每个字段生成专用文本。例如 `uart.write` 的 symbol 查询重复 UART/USART/serial 和 write/send/transmit，以防 `write` 这类通用动词支配结果；signature 查询再加入 buffer、length、返回值等契约提示；file/includes 查询更强调 driver、HAL、header 等源码位置语义。

tokenizer 将字段查询和候选字段切成 token，MiniLM 为每个非特殊 token 产生一个向量并做 L2 归一化。公式中的 `q_f_i` 是字段 `f` 的第 `i` 个查询 token 向量，`d_f_j` 是同一字段中候选文本的第 `j` 个 token 向量。对每个查询 token，先计算它与候选字段所有 token 的余弦相似度，取最大值；再对所有查询 token 的最大值求平均。这正是公式中的 `mean_i max_j cosine(q_f_i,d_f_j)`。实现中查询最长 48 token，候选字段最长 64 token，特殊 token 和 padding 不参与平均。

结果 `S_f(q,d)` 表示“候选字段是否能分别覆盖查询中的关键语义 token”。它比整句单向量相似度更适合符号和签名，因为 UART、write、buffer 等词可以在候选不同位置分别找到最相近的 token。原始余弦结果位于 `[-1,1]`，实现再映射到 `[0,1]`；五个可用字段按 `0.34/0.28/0.18/0.12/0.08` 加权，空字段被跳过并对剩余权重重新归一化，得到 `field-late-interaction` 分数。

追问：为什么叫“迟交互”？这里的过程是否可以概括为：对于某一个能力操作，对所有候选函数计算分数，然后取前五个？这里的候选函数是全部函数吗？编码、查询、计算分数，举一个例子详细说明该过程。

回答：“迟交互”描述的是查询与候选文本发生细粒度交互的时机。双塔整句检索会先把查询和候选各压缩成一个向量，再计算两个整句向量的相似度；交叉编码器则从 Transformer 输入层开始把查询和候选拼在一起，让二者进行“早交互”。本方法介于两者之间：查询和候选的各字段先由同一个冻结编码器**独立编码**成 token 向量序列，直到得到这些向量后，才在 MaxSim 阶段让每个查询 token 与候选字段的所有 token 比较，因此称为 late interaction。这样既保留了 UART、write、buffer 等局部语义的分别对齐，也允许候选字段向量预计算和缓存，计算量明显低于对每一对查询—函数运行交叉编码器。

这里不能简单概括为“对 SDK 全部函数打分后直接取前五个”。完整过程分为候选生成、字段评分和结构化重排三步。Ingestor 首先从源码中恢复具有函数体的函数实体集合 `F(I)`；对于能力 `uart`，能力预筛选器根据符号、路径、签名、include、调用和宏上下文计算 `P_cap(uart)(d)`，只把至少具有一项正向 UART 证据的函数放入能力候选池。因此候选不是 IR 中的文件、宏、类型或任意声明，也不是毫无 UART 迹象的全部函数。`uart.write`、`uart.read` 等同一能力下的不同操作共享这个高召回能力候选池，但会使用不同的操作查询和冲突规则分别评分。字段迟交互对池内每个函数产生 `S_field`，随后还要与静态分数、源码角色、操作契约和 API 家族约束组合；最终 Top5 是完整 q4 方法的输出，并不等同于单独按 `S_field` 截取的前五名。

以 `uart.write` 和候选 `HAL_UART_Transmit(UART_HandleTypeDef *huart, const uint8_t *data, uint16_t size, uint32_t timeout)` 为例：系统从 IR 取出 `symbol=HAL_UART_Transmit`、完整 `signature`、被调函数 `calls`、所在路径 `file` 和头文件 `includes`。symbol 查询可组织为“uart usart serial write send transmit”，signature 查询则强调“send buffer data length size return”。MiniLM 的分词器把这些文本转换为 token/subword ID，编码器为每个 token 产生归一化向量。对于 symbol 字段中的查询 token `uart`，系统在 `HAL`、`UART`、`Transmit` 等候选 token 中寻找余弦相似度最大的一个；对 `write`、`send` 和 `transmit` 也分别执行同样操作，再对所有查询 token 的最大值求平均，得到该字段的 `S_f(q,d)`。signature、calls、file 和 includes 各自重复这一过程；空字段不参与，剩余字段按 `0.34/0.28/0.18/0.12/0.08` 重新归一化后得到 `S_field`。如果另一个候选是 `HAL_UART_Receive`，它可能在 UART 能力 token 上得分较高，却会在 write/send 方向和操作契约上失分；如果候选是低层的 `LL_USART_TransmitData8`，字段语义可能较强，但最终是否成为首位还取决于源码角色和公共层候选是否存在。这里的数值比较来自实际向量计算，示例只用于说明步骤，不预设某个函数必然正确。

```text
S_f(q, d) = mean_i max_j cosine(q_f_i, d_f_j)
```

结构化检索阶段还计算静态操作匹配、字段语义、符号词法、签名契约、源码角色、操作契约、层级路由、调用图邻域和 API 家族等通道。RRF 作为独立融合基线和可审计特征保留；最终 q4 策略不直接使用 RRF 分数，而是采用高精度首位、条件层级回退和家族覆盖解码。

问题：分别形成召回通道对应的具体内容和操作是怎么样的。静态操作匹配、符号子词、签名契约、源码角色和调用图邻域这几种方法分别是什么具体内容。RRF 合并是什么。

回答：代码中实际计算八类可排序通道。`static` 通道由能力词、动作精确/子串匹配、规范顺序、签名提示、调用上下文、公共 API、HAL/控制器层和解析置信度等加权，并扣除相反动作、语义冲突、反向 OS 适配、私有实现和示例测试。`field` 通道就是五字段 token MaxSim。`lexical` 通道把符号分词后计算能力/动作覆盖，并用字符 3-gram Jaccard 处理 CamelCase、下划线和厂商前缀差异，再以 0.78 符号词法加 0.22 签名契约组合。

`scope` 通道以 0.68 源码角色先验加 0.32 符号词法，强调公共 HAL、驱动和公开头文件。`contract` 通道根据该操作的优选词、冲突词、参数化开关和角色先验评分。`layer` 通道为 `role_prior × capability_match × operation_match`，要求候选同时处于合适源码层、包含目标能力，并满足目标动作。`graph` 通道先以静态、字段和词法形成种子分数，再沿 IR 中一跳 caller/callee 关系传播；一个低文本相似候选若被高置信公共 API 调用，或调用高置信 SDK 实体，可获得邻域支持。`family` 通道先按符号形态划分 API 家族，再把家族中最强成员的证据部分传播给同族成员，用于发现阻塞、中断、DMA 等同族实现。

RRF 即 Reciprocal Rank Fusion。每个通道先独立产生名次 `rank_k(d)`，再计算 `sum_k w_k/(40+rank_k(d))`，其中项目使用的通道权重分别为 static 1.0、field 1.2、lexical 1.3、scope 0.9、contract 1.5、layer 1.6、graph 0.7、family 1.1；结果再归一化到 `[0,1]`。RRF 融合的是名次而不是直接混合原始分数，可以缓解不同通道量纲不一致的问题。需要特别说明：当前最终 `complete_structured_scores()` 的 q4 主方法没有直接把 RRF 作为最终排序分数；RRF 被保留为对照、审计特征、轻量学习模块的结构输入和难负例采样依据。原文若写成“最终方法由 RRF 合并全部通道”会夸大 RRF 的实际作用，因此已经修正。

追问：这里多通道和前面编码计算分数是什么关系？这里的每一个通道的过程是否可以概括为：对于某一个能力操作，对所有候选函数计算分数，然后取前五个？这里的候选函数是全部函数吗？并附上举例说明。

回答：前面的五字段编码是多通道中的 `field` 语义通道，而不是多通道之前完全独立的另一套流程。所有通道共享同一个“能力级高召回候选池”，但从不同角度观察同一函数：`field` 读取五个文本字段的神经语义；`static` 读取能力词、动作词、签名提示、调用和宏上下文；`lexical` 处理符号子词与字符 n-gram；`scope` 强调源码角色；`contract` 判断动作方向、参数形态和冲突词；`layer` 联合角色、能力与操作匹配；`graph` 使用调用邻域；`family` 使用 API 命名与实现族关系。因而编码计算得到的 `S_field` 是候选的一项证据，其他通道补充它无法稳定判断的源码层次、方向、调用关系和多实现结构。

从计算形式看，多数通道确实会对某一 `capability.operation` 的池内所有候选产生一个分数或名次，但不是每个通道先各自截断为 Top5 再交给最终方法。系统保留各通道对候选池的排序和分项证据，RRF 基线可以把这些完整名次融合为另一条排序；当前 q4 主方法则只直接用 `static` 与 `field` 形成高精度首位分数，在首位可疑时加入 `contract` 与 `layer` 条件回退，再利用 family 结构生成最终 Top5。`lexical`、`scope`、`graph` 和 RRF 仍用于独立基线、审计、家族/结构支持、困难负例及轻量学习实验，但不能写成全部都直接相加到了 q4 最终分数中。

仍以 `uart.write` 为例，能力预筛选后可能留下 `HAL_UART_Transmit`、`HAL_UART_Receive`、`LL_USART_TransmitData8`、示例函数 `uart_echo` 和内部中断辅助函数。字段通道可能因为名称相近而同时提高 Transmit、Receive 和 echo 的分数；static/contract 通道会奖励 transmit/send 方向并惩罚 receive/read；scope/layer 会把公共 HAL 或正式 SDK driver 放在示例包装与内部辅助函数之前；graph 会记录公共 API 与底层发送原语的调用联系；family 会识别阻塞、IT 和 DMA 发送变体。最终首位通常应是契约正确且复用层次合适的发送接口，Top5 再保留有意义的同族变体和兼容层候选。可见“前五名”是多种证据协调后的受约束输出，而不是八个通道各取五个后简单拼接。

本阶段目标是把正确 API 放入可重排候选集合，而不是直接作最终选择。

### 4.2 SDK 层级路由与操作契约

源码角色分类器把实体划分为：

- public HAL；
- vendor LL/PDL/driverlib；
- SDK driver/source/header；
- OS adapter；
- middleware；
- example/test/documentation。

操作契约进一步区分外设子模式、动作方向和参数化开关。例如基础 timer 对 PWM、Encoder 和软件 timer 施加冲突证据；系统 interrupt 对 SDIO/Wi-Fi/bus IRQ 施加冲突证据；`set_enabled(bool)` 不受简单反义词惩罚。

问题：层级路由是什么？源码角色分类器把实体划分为几种情况，这里的对象是函数实体还是所有的类型？操作契约进一步区分外设子模式、动作方向和参数化开关，操作契约是哪里来的，是经验规则吗？施加证据冲突具体是什么，怎么执行的？下面的层级与契约分数定义具体解释，并说明这个分数代表了什么。

回答：层级路由是利用 SDK 的源码组织层次决定“应优先在哪一层寻找可供 RTOS 调用的 API”。它不是把低层函数永久删除，而是给候选分配层级先验，并在公共 HAL、低层驱动、示例包装和反向 OS 适配并存时优先选择调用方向正确、复用边界稳定的层。当前分类对象是进入语义候选池的**函数实体**；文件路径和符号名是分类特征，文件实体、构建规则和链接资产本身不参加这个函数角色分类。

实际实现共有十种返回类别：`public-hal`、`vendor-low-level`、`sdk-driver`、`public-header`、`sdk-source`、`os-adapter`、`middleware`、`example-test`、`documentation` 和 `unknown`。对应先验大致从 public HAL 的 1.00、SDK driver 的 0.90、vendor low-level 的 0.86，到示例测试的 0.06、文档的 0.02。先验不是正确性概率，而是对 BSP 复用边界的偏好；当 SDK 只暴露低层接口时，低层候选仍然可以胜出。

操作契约是由目标设备模型和一般驱动语义人工制定的领域规则，可以称为“专家定义的、厂商无关的软约束”。它不是从板卡 SDK 真值直接拟合的，也不应包含某个厂商具体函数名。契约的依据包括 RTOS 设备操作的方向、参数角色和设备子模式，例如 timer.start 应指向基础硬件定时器启动，而不是 PWM、Encoder、HallSensor、RTC 或软件定时器；interrupt.register 应指向系统控制器或目标 IRQ 的处理函数注册，而不是 Wi-Fi/SDIO/bus 局部中断。

“施加冲突证据”不是简单删除候选。系统把候选符号、签名和路径分词，统计与 `reject` 集合的交集，得到负项 `negative`，并在 `_operation_contract_score()` 中以 `-0.55 × negative` 扣分；静态操作分数还会扣除 opposite-action、semantic-conflict、reverse-os-adapter、private-api 和 test-example。对于 `set_enabled(bool)`，系统识别 `parameterized-toggle`，先从冲突集合中移除 enable/disable/start/stop 等机械反义词，再加少量 toggle bonus，避免把一个同时实现开关两种方向的合法接口错误惩罚。所有正负命中都可以记录为证据，因此属于软约束而非不可解释的黑名单。

公式 `S_h = 0.25 S_static + 0.25 S_field + 0.25 S_contract + 0.25 S_layer` 中，`S_static` 是可解释静态操作分数，`S_field` 是五字段迟交互分数，`S_contract` 是操作契约分数，`S_layer` 是层级路由分数，四者均缩放到近似 `[0,1]`。`S_h` 表示候选在“动作匹配、跨命名语义、设备契约、源码层次”四个维度上的综合适配程度。系统先用 `S_p=0.5S_static+0.5S_field` 获得高精度首位；只有该首位契约低于 0.18、角色先验低于 0.78，或存在明显更强的公共层候选时，才改用 `S_h` 决定首位。这就是“条件层级回退”，目的是让层级约束纠正可疑首位，而不是无条件覆盖可靠的语义结果。

层级与契约分数定义为：

```text
S_h = 0.25 S_static + 0.25 S_field + 0.25 S_contract + 0.25 S_layer
```

首位仍由高精度静态/字段融合提供；只有首位契约弱、来源层较低或存在更强公共 HAL 候选时，才回退到层级路由结果。

### 4.3 API 家族覆盖解码

函数标识符被归一为 API 家族，例如 `HAL_TIM_Base_*`、`HAL_TIMEx_*`、`mtb_hal_clock_*` 和 `sysctl_clock_*`。解码器固定保留首位候选，再按以下顺序填充 Top5：

1. 首位家族中的高契约兄弟；
2. 更高抽象层的兼容家族代表；
3. 补位家族的一个高契约兄弟；
4. 多通道层级融合的剩余候选。

最终 q4 策略允许首位家族最多提供 4 个候选。该策略解决一个操作存在多个首选/替代接口时，普通 pointwise 排序只返回一个名称最相近函数的问题。

### 4.4 v1.2 核心方法修正：通用操作适配与低分诊断

v1.2 对核心方法作了两项实质修改。第一，在 4.2 的层级契约中使用 `S_generic`，用于区分 RTOS 设备模型需要的通用操作与 SDK 中的专用模式。该分数由动作证据、通用能力根、控制器证据和专用模式惩罚构成，例如通用定时器操作优先 `Base/Timer` 家族，并抑制 PWM、Hall、Encoder 和 LPTimer；通用时钟操作抑制 UART/I2S 等外设专用时钟；中断注册优先 PLIC/NVIC/SysInt 等控制器 API。增强层级分为：

```text
S_certified = S_h + 0.16 S_generic + 0.05 S_role
```

首位仍先由 `S_precision` 产生；当候选存在显著更强的操作契约、通用操作适配度或公共源码层证据时，才回退到 `S_certified`。这些条件是确定性的，不使用 SDK 真值训练。

第二，运行时取消选择性拒答。系统在 `S_precision` 与条件回退后的 `S_certified` 上完成最终排序，只要候选池非空就把 Top1 写入绑定计划。系统同时计算最终分数、唯一符号间隔、八通道实体/家族一致率、操作契约、RRF 和源码角色，将不足项写入 `ranking_evidence.low_score_reasons`。这些字段只用于提示人工优先复核，不改变 Top1，也不再产生自动接受覆盖率。

需要特别说明：当前规则是在三套板卡错误分析后形成的，因此即使不进行梯度训练，也存在人工规则过拟合风险。其有效性必须按所有已有真值 SDK 评测，不能只用50个板卡查询证明。

问题：解码器固定保留首位候选是什么意思？首位候选是哪里来的，和4.1召回与4.2SDK 层级路由与操作契约分别有设么关系？按以下顺序填充 Top5，这一步是什么意思，有什么用，可举例说明。

回答：“固定保留首位候选”表示进入 API 家族多样化阶段后，解码器只调整第二名到后续名次，不再把已经通过高精度/条件回退选出的首位降级。首位先由 `S_p=0.5S_static+0.5S_field` 产生；如果该候选触发弱契约、低源码层或更强公共层条件，则改由 `S_h` 产生。因而 4.1 提供跨命名语义，4.2 提供角色和契约纠偏，两者共同决定首位，4.3 的家族解码负责补齐候选集合。

“填充 Top5”是把剩余候选按结构约束安排到第 2～5 位。若首位来自可信源码层并具有家族键，先选择同一 API 家族中动作契约满足要求的兄弟函数；随后选择尚未出现、且源码角色和契约达到阈值的兼容公共家族代表；必要时再加入该补位家族的一个兄弟；最后按层级综合分补足。q4 表示首位家族在 Top5 中最多占 4 个位置，而不是无条件一定占 4 个。

例如 `uart.write` 的首位若为 `HAL_UART_Transmit`，同族 `HAL_UART_Transmit_IT` 和 `HAL_UART_Transmit_DMA` 可能分别提供阻塞、中断和 DMA 发送实现，适合进入后续名次；另一个公共层的 `LL_USART_TransmitData8` 可以作为兼容家族代表。普通 pointwise 排序容易把多个名字相近但无关的 wrapper 连续排在前面，或只留下一个发送函数；家族覆盖解码在不牺牲首位的前提下，让 Top5 同时包含同族多实现和另一抽象层的可迁移候选，提高 Recall@5，并为后端或人工选择提供余量。

追问：API 家族覆盖解码这部分的意义是什么？为什么叫解码？不能说只是为了提高召回率这个指标而去做的工作。项目中我看到有自动接受覆盖率为 0.38，这个指标是什么意思？这么低的话说明什么，在论文里可以不提。

回答：API 家族覆盖解码的工程动机不是“为了把 Recall@5 做高”，而是把一个操作的点式候选分数转换成**可供迁移决策使用的结构化候选集合**。一个 RTOS 操作往往不是只对应一个厂商符号：UART 发送可能同时有阻塞、中断和 DMA 版本，也可能同时存在公共 HAL 与低层 LL 接口。单纯按相似度取 Top5 容易得到五个重复包装、示例函数或同一错误方向的名称，后端和人工都缺少可用替代项。家族覆盖规则先保护已经过高精度排序或层级回退确定的首位，再按动作契约、源码角色、家族兼容性和多实现覆盖选择后续候选。这样做的实际价值是：首位直接用于自动绑定；当目标 RTOS 配置、DMA 能力、阻塞语义或编译闭包不兼容时，后续候选提供同族或跨抽象层的可追溯替代方案；低分操作需要复核时，人工面对的是经过结构整理的候选集，而不是名称相近的冗余列表。Recall@5 只是衡量这种“可用替代项是否被覆盖”的外部指标，而不是设计该机制的唯一理由。

这里称为“解码”，是因为输入已经不是原始源码，而是每个函数的连续分数、首位、角色、契约和家族标签；算法需要在“首位固定、家族配额、角色阈值、契约兼容和 TopK 容量”等约束下，解出一个有顺序的离散列表。它与序列模型中的 beam decoding 含义不完全相同，更准确的论文术语可以写成“API 家族约束解码”或“受约束候选集解码”，并在首次出现时说明这是从点式排名到结构化 TopK 的确定性转换，避免让读者误以为系统使用了生成式解码器。

旧自动接受覆盖率 0.38 表示历史版本在50个板卡操作查询中只允许19个写入绑定计划。当前任务假设五类通用能力操作在目标 SDK 中存在可调用实现，v1.2 因而取消这层拒答并始终选择 Top1。覆盖率不再是当前方法指标，也不进入论文主表；历史数值只在 `research-status.md` 保留，用于解释版本演进。

取消覆盖率不等于可以只报告高分子集。当前可靠性直接按每套真值中**全部可达查询组**计算 P@1、Recall@3/5、MRR、MAP 和 nDCG@10，且必须写明 SDK 数和查询组分母。低分/弱证据清单属于工程诊断，不从指标分母中移除。三套板卡50组结果只能作为错误分析和实板对象的分组结果，不能替代全部已有真值 SDK 的主结果。

问题：第四章核心方法只保留以下三个组成部分。这里完整的工作流程是什么，三个方法是可以独立的吗？在这里三个部分怎么组合起来的？

回答：三个组成部分是**顺序协作的一个方法**，不是三套互不相干的排序器。完整流程为：先从 IR 取得某个操作的函数候选池和五字段；字段迟交互为每个候选产生 `S_field`，静态特征同时产生 `S_static`；源码角色、操作契约和通用操作适配度产生 `S_layer`、`S_contract` 和 `S_generic`；系统以 `S_precision` 形成首位，并按固定条件回退到 `S_certified`；随后用首位的 API 家族、角色和契约信息执行 q4 覆盖解码，得到最终 Top5；只要候选池非空就选择 Top1，并根据真实决策间隔、八通道一致性、契约、RRF 和源码角色附加低分/弱证据标记。输出再转换成 OS 无关的绑定计划，成为闭包求解的种子。

从软件架构看，字段编码、层级契约评分和家族解码具有清晰接口，可以分别替换、做消融或单元测试；从论文方法看，它们不可被描述为彼此独立的最终方案，因为后一步明确消费前一步产生的分数、首位和家族信息。正确表述应是“模块化实现、顺序组合、联合形成最终方法”。

问题：以上所有步骤是不是都不需要通过sdk语义真值进行训练？所有规则都是静态的？我是否可以理解为，现在的指标比之前优秀，只是因为现在的规则比以前的规则更完善（融合了三套规则）？如何解释“当前语义分析是否只是一些静态规则脚本的集合？”

回答：当前论文主方法在运行时**不读取真值标签，也不训练基础编码器**。MiniLM 使用公开预训练权重并冻结；源码角色、操作契约、通用操作适配度、条件回退、q4 解码和低分诊断判据都是确定性的领域规则。真值只用于最终计算 P@1、Recall@3/5、MRR、MAP 和 nDCG，不用于拟合参数或校准阈值。由于板卡探索集被多次用于错误分析，规则设计仍有人工过拟合风险，必须用冻结后的独立确认集验证。

字段迟交互来自预训练语义表示，层级、契约、通用适配度和家族解码属于确定性领域约束，因此方法本质上仍是“冻结的轻量神经语义编码 + 可解释的领域约束 + 组合解码”。但全量结果表明，板卡子集上的大幅提升没有稳定迁移到全部SDK：自动真值全量P@1仅为0.662，H01/H02分别为0.381和0.414。现阶段不能再用板卡子集的1.000/0.936说明总体方法已经达到目标。

也不能把当前方法包装成完全学习化模型。更准确的定位是**神经语义特征与确定性结构约束结合的混合检索方法**。静态规则的优点是小模型、低资源、可审计且便于跨 SDK 迁移；风险是规则可能带有开发集偏差、覆盖新设备类型时需要扩展契约。论文应通过规则基线、字段方法、层级契约和家族解码逐步消融，以及独立确认集，证明每部分的增益和泛化，而不是以“用了 AI”替代方法论证。

追问：现在确定，论文的工作就固定到这三个方法，不把下面的学习模块作为内容。那么，现有的内容是否可以包装为一个专家系统，对于论文的层次是否会有一些帮助？目前的论文的说辞我感觉太不直观了，评审人看到肯定不知道在说什么，我们的方法是属于什么领域的就要说清楚，这样前面也能介绍相关领域的知识作为相关工作，评审的人看到会有一个基本的概念。

回答：现有方法确实具有“专家知识参与推理”的特征，但不建议把整套方法直接命名为传统专家系统。若按专家系统的经典构成解释，设备操作契约、相反动作、源码角色先验、层级回退条件和 API 家族规则可以视为知识库；条件回退与家族约束解码可以视为推理过程；分项分数、entity_id 和来源位置构成解释记录。因此把这部分称为“领域专家约束”是成立的。然而系统的候选语义主要来自冻结 MiniLM 的 token 表示与 MaxSim 检索，输出也是连续排序和诊断结果，而不是在符号事实库上进行完整的逻辑演绎。若全文只用“专家系统”包装，评审人可能把工作理解为手工规则库，反而弱化跨命名语义恢复、代码检索和受约束排序的技术贡献，也会追问规则完备性、知识获取和推理一致性等并非本文重点的问题。

更准确、也更直观的领域定位是：**面向嵌入式软件迁移的领域知识引导语义代码检索（domain-knowledge-guided semantic code retrieval）**，方法类型可进一步概括为**轻量神经语义表示与符号约束结合的神经符号/混合检索方法**。从软件工程任务看，它位于代码智能、API 映射与推荐、自动软件迁移和嵌入式系统工程的交叉处；从方法看，它属于字段感知语义检索、知识引导排序、受约束 TopK 解码和可解释诊断。这样的定位能让评审先把问题理解为“在陌生 SDK 中检索并绑定满足 RTOS 设备操作契约的函数”，再理解为什么单纯代码搜索不足，以及源码层级和 API 家族约束如何解决领域歧义。

论文可以采用如下直观主线：“BSP 迁移中的核心语义任务，是给定 RTOS 设备操作契约，从芯片 SDK 中检索、排序并选择可迁移 API；本文提出一种领域约束的语义代码检索方法，以字段迟交互恢复跨厂商命名语义，以源码角色和操作契约纠正抽象层及动作歧义，再以 API 家族约束解码形成可绑定且具有替代项的候选集合。”这句话明确了任务、方法类别、三个组成部分及其顺序。BSPForge、Migration IR、闭包和编译诊断则作为端到端验证载体，证明检索结果能进入 RTOS 工程，而不是再与核心语义方法争夺“第四个创新点”。

相应地，相关工作可按四条线组织：第一，语义代码搜索与神经代码表示，说明整句向量、token 迟交互和字段检索的基础；第二，API 映射、API 推荐与软件迁移，说明从功能需求到源 API 的对应问题；第三，知识引导或神经符号检索、受约束排序与多样化 TopK，说明结构知识如何校正纯语义相似度；第四，编译反馈和可解释软件工程诊断，说明排序选择如何进入可构建、可追溯的工程闭环。嵌入式 BSP/驱动迁移作为应用背景贯穿这些方向。可以在方法描述中使用“专家知识”“领域规则”或“符号约束”，但论文类型最好仍定位为代码智能与自动软件迁移，而不是笼统的 AI 专家系统。

这种重新定位有助于论文表达和相关工作组织，但**术语包装本身不会提高论文层次**。真正决定层次的仍是：任务定义是否新且重要，三部分是否形成不可替代的完整方法，独立 SDK 上的全量准确率、召回率、消融和统计结果是否证明泛化，以及三块实板和双 RTOS 是否形成端到端证据。历史训练探索不进入摘要、核心方法或主结果，避免主线再次变散。

## 5. 当前方法边界

v1.4 的运行时默认主线不包含 SDK 监督训练、训练真值构造或学习式字段门控。MiniLM 仅使用公开预训练权重并冻结推理；SDK 真值只在离线评测阶段计算指标，不进入 q4 排序、低分诊断或运行时绑定。

v1.6 新增一条边界清楚的候选方法：冻结预训练代码编码器，只用 H02 正例-未标注查询内偏好训练 12,636 参数的查询适配和效果融合头。该方案独立于 q4，暂未替换 Resolver 默认路径；是否进入论文最终核心方法，应由新增确认 SDK、多随机种子和板卡端到端结果决定。论文撰写时不能把无训练 q4 指标与 H02 训练方法指标混成同一实验口径。

## 6. 原型系统的定位

原型仍由六个工程模块构成，但它们不是六个并列创新点。

| 模块 | 论文定位 |
| --- | --- |
| SDK Ingestor | 为方法提供统一 Migration IR 输入 |
| IR Store | 保存版本、实体 ID 和证据位置 |
| Semantic Resolver | 承载本文三个核心算法组成部分 |
| Closure Solver | 形成可编译工程所需的构建资产闭包 |
| Build Diagnoser | 将真实工具链错误转成闭包约束并自动迭代 |
| OS Backend | 生成 RT-Thread/Zephyr 原生工程和设备注册代码 |

论文方法贡献集中在 Semantic Resolver；其他模块共同证明方法不是脱离构建系统的离线排序实验。

## 8. 工程闭环证据

K210/RT-Thread 使用 `operation-structured` 运行时方法：

- 生成 19 个操作绑定；
- 首轮链接发现 `sys_register_getchar` 等缺失符号；
- Build Diagnoser 从 IR 定位并补入 `lib/bsp/syscalls.c`；
- 第二轮构建成功；
- 输出 RISC-V ELF/BIN；
- 19/19 绑定得到编译、链接和产物验证反馈。

完整运行耗时 259.67 秒，其中语义解析 120.39 秒、两轮构建 105.71 秒。编译成功仍不证明外设运行语义，三块板卡回归需要单独报告。

## 9. 论文贡献的推荐写法

论文贡献建议收敛为三点：

1. 提出层级约束的字段迟交互与 API 家族覆盖解码方法，解决异构 SDK 中抽象层混杂、设备子模式混淆和多实现漏召回问题。
2. 实现端到端 BSPForge 原型，将语义绑定与构建闭包、自动诊断和两种 RTOS 原生后端连接，生成可验证固件。
3. 构建跨 25 套 SDK 的操作级评估体系，在 20 个独立开发来源和三套板卡 SDK 上报告全量排序、低分诊断、编译、仿真与后续实板证据。

不要把四级真值、RRF、每条规则、每个后端或每个工具脚本分别列成创新点。它们是上述三项贡献中的实现与评估组成部分。

## 11. 当前结论边界

当前可以声称：系统已经实现无SDK监督训练的结构化排序、通用操作适配、Top1 固定选择和运行时低分诊断，并在三套拟上板SDK子集及K210构建闭环中证明了工程可执行性。全量真值结果尚未达到论文预设指标，因此现阶段不能仅凭三套板卡子集证明语义分析总体可靠。

当前不能声称：

- 对未见厂商已完成确认性泛化验证；
- 当前语义排序已经在全部已有真值SDK上达到目标；
- 三套板卡的高分结果可以代表全部 SDK 的泛化性能；
- 自动弱真值等同于人工金标准；
- 编译成功等同于设备运行正确；
- 三块板卡已经完成真实外设回归。

正式论文应冻结当前代码和 q4 参数，增加未用于错误分析的 SDK 做一次性确认测试，并完成第二人真值复核。

## 13. 候选升级：预训练代码效果排序 v0.2

### 13.1 方法定位

新方案把语义决策从“冻结 MiniLM 字段表示加确定性契约”推进到“读取实际函数实现的预训练代码语义加跨过程硬件效果”。输入仍是同一 Migration IR，但候选序列化增加归一化函数体、调用关系和寄存器标识；冻结 `jina-embeddings-v2-base-code` 建立实体缓存，秩 8 查询残差学习 19 个操作在代码空间中的任务方向，22 维寄存器效果图提供显式结构证据。

H02 中 `label > 0` 是正例，`label == 0` 是未标注项。模型只学习同一查询内“正例应排在采样未标注项之前”的相对偏好，不把未标注函数声明为确定负例。直接联合学习图融合在部分厂商折上过拟合，因此最终候选方法在每个外折的训练 SDK 内部验证代码/图比例，再对未见厂商做 OOF 评测。

### 13.2 当前结果

本轮只处理 281 个具有可达函数正例的 H02 训练角色查询，137 个 `no_public_api` 组按用户确认暂不考虑。18 个独立厂商/上游组五折结果如下：

| 方法 | P@1 | Recall@5 | MAP | nDCG@10 |
| --- | ---: | ---: | ---: | ---: |
| v1.5 寄存器效果图 PU | 0.335 | 0.528 | 0.432 | 0.506 |
| 冻结代码模型零样本 | 0.399 | 0.568 | 0.480 | 0.549 |
| 低秩查询适配 | 0.427 | 0.610 | 0.517 | 0.583 |
| 嵌套校准代码/图融合 | **0.495** | **0.653** | **0.565** | **0.639** |

最终方法相对 v1.5 的四项提升分别为 0.160、0.125、0.133 和 0.134，查询级配对 bootstrap 95% 区间均不跨 0。Top1 错误由 187 降至 142，同 API 家族动作混淆由 61 降至 37。该结果证明预训练代码表示、函数体输入和轻量任务适配具有增量价值，但绝对指标仍低于既定目标。

三块历史板卡的 50 个诊断组上，适配方法低于零样本和 q4；该子集已经被历史开发反复查看，也不是干净确认集。当前合理结论是把 v0.2 作为更有理论上限的论文候选方法继续验证，而不是立即替换已经能生成六组固件的 q4 运行路径。

### 13.3 与原三部分的关系

若后续确认实验继续支持 v0.2，论文核心方法可以收敛为：

1. IR 感知的函数实现序列化与冻结预训练代码表示；
2. 寄存器效果锚定的跨过程图与正例-未标注低秩偏好适配；
3. 训练 SDK 内嵌套校准的代码/结构证据融合。

原有源码层级、操作契约和 API 家族解码可以降为硬约束、候选构造和工程输出机制，不再分别包装成并列创新点。若确认集不支持 v0.2，则保留原 q4 为论文主线，并把 v0.2 作为预训练代码模型消融和后续工作。详细算法、模型提交、数据流、统计和复现命令见 `docs/pretrained-code-effect-ranking-v0.2.md`。

## 14. 候选升级：硬件效果多视图与轻量分级排序 v0.3

### 14.1 新增方法

v0.3 不再把完整函数体当作唯一证据。系统增加操作条件局部代码视图，并把完整代码语义、局部效果语义、22 维硬件效果图和结构化 IR/契约特征交给同一轻量排序器。局部视图根据当前 `operation_id` 优先保留能力/动作词、寄存器读写、效果路径调用、赋值和位运算，并加入相邻上下文。

本轮比较了两类学习器。25,196 参数多视图神经排序器虽然加入同 API 家族难负例、分级权重、12/24/36 轮训练和 listwise 损失，但严格嵌套结果退化为 P@1 0.395、Recall@5 0.572、MAP 0.483、nDCG@10 0.559，证明当前数据规模不足以稳定学习端到端融合。该路线作为负向消融保留。

分级 LambdaMART 直接学习 0/1/2/3 相关性和多视图非线性交互。经过 5/7/9/13 叶、L1/L2、特征与样本子采样的受控搜索，严格厂商嵌套选择达到 **0.651/0.748/0.681/0.743**，相对 v0.2 分别提高 0.157/0.095/0.117/0.103。固定 small-bagged 配置为 0.648/0.757/0.685/0.747，只作为探索性配置报告，不能替代新的确认 SDK。

固定参数消融表明，完整代码加入当前局部效果切片后为 0.388/0.589/0.478/0.548，相对完整代码的 0.399/0.577/0.478/0.551 没有稳定增益；加入硬件效果图后升至 0.520/0.708/0.605/0.677，再加入结构契约达到 0.641/0.769/0.683/0.745。后两步提升区间均不跨 0。因此当前已验证核心是寄存器效果图、结构契约和轻量分级交互，局部切片只作为待改进辅助视图。

Top-K 查询-候选冻结联合编码也经过 12/24/36 轮和两种 listwise 权重比较。固定最优为 0.488/0.674/0.562/0.638，严格嵌套为 0.431/0.628/0.520/0.602；所有内层都选择联合权重下限 0.5。该结果说明通用嵌入模型上的拼接编码不能代替真正的任务交叉编码器，因此联合方案同样保留为负向消融。

### 14.2 论文核心方法的进一步收敛

若后续确认实验支持 v0.3，论文方法建议表述为：

1. **寄存器效果锚定的语义证据构造**：从 Migration IR 恢复函数实现、寄存器效果路径、源码层级和操作契约，并保留操作条件局部视图作为辅助证据；
2. **轻量多视图分级排序**：冻结小型代码模型，用分级树排序学习完整语义、局部效果、硬件图和结构契约之间的非线性交互；
3. **硬约束保护与工程闭环**：用动作冲突、源码角色和签名可封装性约束最终排序，再把绑定交给闭包、诊断和双 RTOS 后端验证。

LambdaMART、难负例、树叶数和短名单不是独立创新点，而是第二项贡献的实现与实验因素。SDK 摄取、闭包求解、自动诊断和 OS Backend 继续作为端到端系统贡献，不能与语义方法割裂。

### 14.3 当前结论

v0.3 的 281 条 OOF 预测中 Top1 正确 183 条、错误 98 条。主要错误为一般排序混淆 40 条、同族动作混淆 26 条、真值效果路径缺失 15 条。绝对指标仍未达到预设 0.80/0.90/0.80/0.80，因此当前只能声称方法相对 v0.2 有明显增量，不能声称语义绑定已经普遍可靠。

完整方法、配置搜索、联合编码候选和后续路线见 `docs/effect-slice-multiview-ranking-v0.3.md`；逐查询错误见 `docs/effect-slice-multiview-error-report-v0.3.md`。

## 15. 跨操作效果对比探索 v0.4

v0.4 对同一 SDK 实体建立同能力多操作效果画像，用目标操作相对竞争操作的效果差补充 v0.3。固定模型消融中三项效果对比显著提高 P@1 和 MRR，但严格厂商嵌套未超过 v0.3；API 家族一致性、多信号差分和内层权重融合也没有得到稳定显著结果。因此当前核心方法不增加第四项贡献，仍收敛为寄存器效果证据、结构契约和轻量分级排序三部分。

v0.4 的正向结论仅限于“跨操作效果对比是有潜力的纠错信号”；不能写成最终性能升级。家族一致性、契约/词法差分和双专家融合应在论文消融或讨论中简要报告，用于说明方法选择经过受控比较。完整定义、数据隔离和结果见 `docs/cross-operation-effect-contrast-v0.4.md`。

相近论文不存在统一绝对指标录用线。当前 v0.3 数值处于近期代码/API 检索的常见区间，但自动绑定仍应以更高的工程阈值、冻结 SDK、仿真和上板回归验证。文献表和论文写法见 `docs/related-task-metric-reference-v0.4.md`。

## 16. H03 与 LambdaMART 头部目标候选 v0.5

H01/H02 源码仲裁后的 H03 在 284 个可达查询上重新运行 v0.3。严格厂商嵌套结果为 P@1 0.697、Recall@5 0.738、MAP 0.689、nDCG@10 0.751；相对 H02 的 P@1 提高 0.046。H03 平均每组含 2.366 个唯一正符号，因此 Recall@5 表示前五名覆盖全部等价实现的比例；另增加 Hit@5 表示是否至少找到一个正函数，首轮为 0.901。

外部 LambdaMART 建议经过统一消融。显式 Top-5 截断在三个随机种子中的 P@1 为 0.722/0.725/0.711，均值 0.719；硬负样本、符号去重和厂商风格剔除没有稳定超过该配置。Top-5 截断保留为候选训练优化，但配对 bootstrap 区间仍跨 0，尚不替换 v0.3 论文主结果或 Resolver 的 q4 运行时。

严格错误中有 9 个 Top1 是满足公共角色与硬约束的包装函数，并直接调用 H03 正函数，使保守调用等价上界由 0.722 到 0.754。该值只用于漏标复核，不自动改写标签。Recall@5 或 Hit@5 也不能替代 P@1，因为生成器最终只绑定第一名。完整流程、消融、统计和可靠性边界见 `docs/lambdamart-h03-training-optimization-v0.5.md`。

## 17. 冻结 LambdaMART 的计划驱动部署 v2.2

最终部署链以冻结 LambdaMART 为学习排序主体。K210 运行时数据只由 SDK IR 构造，不读取目标板真值；19 个操作共保留 14,814 个候选行。模型原始结果继续单独报告 P@1 0.895、Recall@5 0.775、MAP 0.722、nDCG@10 0.816 和 Hit@5 0.947，部署约束不得反向改写这些指标。

模型分数之后增加通用可执行性解码。第一步检查候选符号是否符合目标能力和动作，并从函数签名解析顶层参数，验证参数数量与 `pin/mode`、`buffer/size`、`irq/callback`、`timer/channel` 等操作契约。第二步以规范能力为单位，求五类能力各自能够覆盖全部操作的共同 API 家族；对每个家族选择各操作中得分最高的兼容候选，以归一化名次和选出最终家族。该过程解决“单项 Top1 看似相关，但多个操作来自不兼容子系统”的问题。

K210 的代表性案例是 `gpio.configure`。原始 Top1 `gpio_init(void)` 缺少 pin 和 mode 参数，不能实现 RTOS 针脚设备的逐引脚配置；它因此被签名约束排除。最终 GPIO 四项统一选择 `gpiohs_set_drive_mode`、`gpiohs_set_pin`、`gpiohs_get_pin` 和 `gpiohs_irq_register`。这不是将错误结果替换为人工真值，而是在不访问标签的条件下，把学习排序转换为满足目标接口契约的可执行组合。

计划生成后，OS Backend 不得再次选择目标函数。RT-Thread 的 18 项操作由生成 C 代码直接调用，PLIC 初始化因 RT-Thread 启动阶段已经完成而由 OS 等价接管；Zephyr 的时钟、UART、GPIO 和定时器共 15 项直接调用，PLIC 四项因中断控制器所有权冲突由 Zephyr 二级 IRQ 框架等价接管。每项处置、实体 ID、函数签名和源码证据写入 `functional-bindings.json`，再由编译反馈逐项关联。辅助函数只能承担初始化补充、参数适配、回调注销、状态清理和工具链访问宽度约束，并与目标选择分栏记录。

论文应把该层定位为“硬约束保护的部署解码”，而不是新的学习模型，也不能把解码后的实板通过率混入原始排序 P@1。核心学习贡献仍是多视图硬件效果证据与 LambdaMART；计划驱动解码负责把统计排序安全地落到可编译的 OS 接口上，双 RTOS 构建和实板结果负责验证端到端可执行性。

最终 K210 实板证据不反向参与模型训练或部署解码。RT-Thread 和 Zephyr 的规范计划均含 19 项操作，编译反馈均逐项可观察；两套固件分别完成 10 次启动和每轮 9 条命令，共 90/90 条通过。RT-Thread 的 UART 测试在正式计数前有界清理复位残留并报告 `discarded_rx_bytes`；Zephyr 对 K210 SDK 的 FPIOA `volatile` 位域强制使用 32 位 MMIO 访问。二者属于测试有效性和 SDK/工具链兼容约束，不改变 LambdaMART 分数、原始候选顺序或签名家族解码结果。
